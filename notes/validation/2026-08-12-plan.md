## 2026-08-12 — Tier 1, V1: golden-case recommendation tests

**Context.** A ~250-line throwaway implementation of the scoring model
(`tests/prototype_engine.py`, runnable with `py -3 tests/prototype_engine.py`;
13 hand-scored weapons, 1 content template) run against 9 assertions that
encode what any experienced player knows to be true.

| # | Case | Result |
| --- | --- | --- |
| T1 | Longbow+Witchwork+Permafrost → recommends a healer | PASS |
| T1b | Weakness list leads with healing | PASS |
| T2 | After healer joins → recommendation flips to frontline | PASS |
| T3 | Empty party → first pick isn't pure DPS | PASS |
| T4 | 2 healers in 4 → no third healer recommended | PASS |
| T5 | 6-DPS party, last slot → healer | PASS |
| T5b | Greedy-trap lookahead flags ≥3 uncovered capabilities | PASS |
| T6 | Known meta comp outscores troll comp by >25% (84.9 vs 19.3) | PASS |
| T7 | Auto-generated "why" leads with the right capability | PASS |

**Decision.** Hard floors are load-bearing. The first run failed 4/9 because
soft targets alone let breadth weapons (Heavy Mace covering five medium
gaps) out-rank a healer fixing the single critical gap. The design doc's
`hard_floor` mechanic (§3.1) — zero healing or frontline is catastrophic,
not merely suboptimal — is a requirement, not an option.

**Evidence.** 9/9 after one design iteration. Caveat: 9 assertions over 13
weapons is a smoke test of model shape, not proof of recommendation
quality; quality is tested in Tier 2.

**Changes.** `hard_floor` in the design and the prototype; the cases live on
as `tests/test_golden.py` T1–T7.

## 2026-08-12 — V1 full-coverage pass

**Context.** The golden suite graduated to `test_golden.py` running against
the built dataset and stays 9/9 with all 137 combat weapons curated (no
illustrative placeholders left).

**Decisions.** Two more load-bearing findings of the V1 class:

- Heal-floor strength: with richer curated data, synergy and meta-prior
  leakage let a breadth pick out-rank every healer for a healer-less party by
  0.014. `penalty_mult` raised 1.5 → 2.0 (PROVISIONAL). The structural fix
  worth testing after Tier 2 is step-function floors (no partial relief).
- Pseudo-tankiness: personal defensive cooldowns (Parry, Deflecting Spin,
  Counter…) scored as `tankiness 1` harvested tank-floor relief and put a
  purge lance above every tank. Rule: momentary defensives ground no
  tankiness. 41 scores removed in one pass.

**Changes.** `scoring.yaml` `penalty_mult`; 41 sheet rows.

## 2026-08-12 — Tier 2: recommendation quality (V3, V4, V5, V5b)

**V3. Next-pick validation round.** Give 10–15 partial parties to 3+
experienced shotcallers; collect each caller's next pick independently;
compare with the engine's top-3. Target: the caller's pick appears in the
engine top-3 in ≥70% of cases. This is the true accuracy metric. The
curation prerequisite is met (all 137 weapons, 2026-08-12) and
`tests/tier2_form.md` is regenerated against the full pool (seed 20260812).
V3 is the critical path; everything else is tuning noise until it runs.
First run 2026-08-23 (`2026-08.md`, "First V3 round"); the V4 gate has since
been re-based to `actual_gear` and enforces via exit code.

**V4. Meta-comp reproduction.** Feed the engine each published meta comp
minus one member; the engine should propose the missing member's role in
its top-3. The automatable version of V3. Case list: `data/published_comps/`
(moved out of `tests/meta_comps.yaml` by chapter 2, 2026-08-19 — production
build data lives in the evidence layer with full provenance envelopes). Two
real entries recorded 2026-08-12, every weapon cell mapped to a catalog key:
(1) shotcaller "Deadlyhooker", large-content ZvZ, 3 parties × 20,
battlemount slots flagged as outside the weapon model; (2) shotcaller
"Timothy", blackzone-roam brawl comp "blap", 1 party × 20, with per-slot
skill loadouts (q/w/p), potions and food — the first real default-kit data
(V5 catch #1 established this has no public statistical source). 20-size
templates exist (`blackzone_roam`, `territory_defense`, 2026-08-12), so the
runner is unblocked — but both took role-ratio calibration from these same
two comps, so leave-one-out against them is weakened evidence (documented in
the template headers). A clean V4 run needs comps from callers whose sheets
did not inform the templates. The golden suite anchors both templates to the
real comps in weak form (T8/T9: fitness discrimination vs troll comps +
healer-floor sanity; 13/13 as of 2026-08-12), and `tests/test_js_parity.py`
holds the browser scoring identical to the Python engine (60/60 random
parties, 1e-9).

**V5. Curation reliability.** Two people independently score 15 weapons;
disagreement >1 point on >10% of cells means the capability definitions are
too vague — tighten definitions before mass curation.

**V5b. Automated evidence lint** (promoted from the V5 findings — a
mandatory CI gate, design doc §6.3): every nonzero capability score must
cite a spell UniqueName; the lint verifies the spell is equippable on that
item (ao-bin-dumps `craftingspelllist`), that its function tags/description
support the claimed capability class, and that its target direction
(enemy/ally/self) matches. Catches fabricated capabilities and direction
errors without waiting for human review.

### 2026-08-12 — Two curation catches that created the lint

**Catch #2.** 1H Mace listed `purge 1`; the weapon has none. Wiki-verified
the full mace ability list: no mace Q/W removes buffs, and 1H Mace's E (Deep
Leap) is a mobility/stun leap. The purge lives on Heavy Mace's E (Battle
Howl, "purges before the silence") — so the original Heavy Mace sheet was
wrong in the opposite direction (purge filed as a W choice when it is
inherent). Both sheets corrected with per-spell citations. Decision: the
data model was reworked so capability sheets exist per item with a mandatory
`evidence_spell` column, and archetype capabilities are computed by
composition, never hand-entered.

**Catch #1 (earlier).** A curation check flagged Longbow's
`knockback_displace 2`: the bow line's Frost Shot knocks the USER back
(repositioning), not enemies, and is not in the standard group kit. Fixed in
the prototype and the design doc. Decision: the taxonomy gained a
directionality rule (self- vs enemy-targeted effects) and a curation lint.
Confirmed hard data limit: no public source records which spells players run
per content (killboard `ActiveSpells` is empty everywhere; every "build
stats" site shows items only), so default kits come from curation per
content type — the only statistical alternative is opt-in client-side
capture, AODP-style (Phase 3+, optional).

## 2026-08-12 — Tier 3: data pipeline claims (before Phase 3 investment)

**V6. Content-labeling accuracy.** Sample 100 battles, hand-label content
type from context, measure classifier agreement. Gate: ≥80% precision on
castle/hellgate/roads labels, else Phase 3 stats stay content-agnostic.

**V7. Coverage at scale.** Rerun V2 across ~200 battles of varied size and
server (script, not eyeball). Gate: ≥85% weapon attribution in 10–50-player
battles. Script exists (2026-08-13): `pipeline/sample_battles.py` samples the
official gameinfo API with per-battle caching, buckets by fight size (small
<12 / mid 12–30 / large >30), writes `out/weapon_usage_v2.json` with a
coverage stat; the dashboard quotes it as display-only "field reports". Check
the coverage number in that file against the 85% gate on each refresh.

**V8. Statistical sanity backtest.** Compute weapon win-lift on 3 months of
data; check that community-consensus-strong weapons show positive lift. If
stats contradict consensus everywhere, the confounds dominate and δ (the
meta-prior weight) stays small.
