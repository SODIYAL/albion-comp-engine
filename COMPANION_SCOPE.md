# Party Companion — Stage 2 Scope

Read-only local Photon packet reader that feeds Comp Forge a live party:
who's in it, their equipment, their **selected spells**, their item power.
Scoped 2026-08-13 from the Statistics Analysis Tool source (repo:
`Triky313/AlbionOnline-StatisticsAnalysis`, read at `main`). Visibility-rule
status: everything below is data the client already renders (party UI,
inspect window) — same tolerated category as SAT itself. Read-only, no
gameplay automation.

## Headline finding: spell picks ARE broadcast

`CharacterEquipmentChanged` (event 90 on the current build — the codes
shift per patch, see the verified map below) carries, for any visible player:

- param 2 — equipment `short[]`, slots 0..9 = MainHand, OffHand, Head,
  Chest, Shoes, Bag, Cape, Mount, Potion, BuffFood
- **param 7 — spells `short[]`: indices 0,1,2 = weapon Q/W/E picks**,
  3 = Armor(D), 4 = Head(R), 5 = Shoes(F), 12/13 = potion/food
  (param 5 = cape spells)

This means the companion resolves the engine's **(QW)-conditional layer**
with real per-player picks — no inspect click required for players who
change gear/become visible. The inspect operation (`GetCharacterEquipment`,
op 148) adds equipment + **ItemPower** on demand (spells not parsed from it
by SAT; possibly present on the wire, unverified).

## Verified event map — LIVE-CONFIRMED via `/schema` (2026-08-14, Realm Divided)

These are the codes the companion actually uses, read off real traffic (the
earlier SAT-enum guesses — 34/95/237 — were a game version behind).

| Purpose | Code | Key params (all live-verified) |
| --- | --- | --- |
| Player appears (name+gear+spells) | event 29 | 0=objId, 1=name, 8=guild, 40=equip `short[10]`, 43=spells `short[14]` |
| Gear/spell change | event 90 | 0=objId, 2=equip `short[10]`, 7=spells `short[14]` |
| Full party roster | event 231 | 9=names `string[n]`, 8=guids `byte[16n]` |
| Self join (name/objId only) | response op 2 | 0=objId, 2=name, 58=guild (52 is item INSTANCE ids — unusable) |
| Inspect (on-demand gear + IP) | response op 148 (SAT enum; shape-bound) | 0=guid `byte[16]`, 1=equip `short[10]`, 3=item power `double` — per SAT `GetCharacterEquipmentResponse`; shipped 2026-09-06, NOT yet live-confirmed |

Equipment slot order (both arrays), confirmed against a real loadout:
`[0]mainhand [1]offhand [2]head [3]chest [4]shoes [5]bag [6]cape [7]mount
[8]potion [9]food`. Spell slots: `[0]Q [1]W [2]E [3]D [4]R [5]F`.

Albion's real event code rides in **parameter 252** (op in 253), not the
Photon code byte. Codes are positional and SHIFT WITH GAME PATCHES — when
`handled_events` stalls at 0 after an update, re-run the `/schema` discovery
(README) and re-map by the parameter SHAPES above (name string, `short[10]`
equipment, `byte[16n]` guid list). Same spirit as the `effect_overrides.yaml`
re-check ritual.

## Build decision: standalone console app, NOT a SAT fork

*(2026-08-13 decision record. What shipped differs in one respect: the
stock `PhotonPackageParser` NuGet only speaks Protocol16, so the parser is
vendored Protocol18 code from SAT — GPL-3.0 for the companion binary,
`companion/photon/NOTICE.md`. Handlers dispatch by parameter SHAPE, not
by the code numbers listed here.)*

- SAT has **no plugin system, no HTTP listener, no live export** — a fork
  means carrying a large GPL-3.0 WPF app.
- The clean path is MIT end to end: NuGet `PhotonPackageParser` 4.1.0 (MIT)
  (+ optionally `Albion.Network` 5.0.1 handler framework), a capture
  provider copied in approach from SAT (either Npcap via libpcap bindings
  or raw sockets — raw sockets need Administrator; BPF filter
  `udp and (port 5055 or 5056 or 5058)`), a handful of handlers
  (visibility, gear change, roster, self-join, inspect), and
  `HttpListener` on localhost.
- Item/spell indices → names: ship lookup tables generated by OUR pipeline
  from ao-bin-dumps (`items.json`, `spells.json`) — the same clone the
  patch procedure already uses. Equipment index → `unique_name`
  (`2H_MACE`), spell index → spell UniqueName (matches sheet evidence IDs).

## Bridge contract (companion → Comp Forge)

`GET http://localhost:53321/party`, CORS-allowlisted to the Pages origin
and localhost (loopback is exempt from mixed-content blocking, so the
public HTTPS page can poll it directly). The live payload — documented
with every field in `companion/README.md` "What it serves":

```json
{
  "ts": "2026-08-13T19:20:00Z",
  "self": "YourName",
  "members": [
    { "name": "Alstroameria", "guid": "…",
      "weapon": "2H_HOLYSTAFF", "weapon_item": "T5_2H_HOLYSTAFF@1",
      "item_power": 796,
      "equipment": { "head": "T6_HEAD_CLOTH_SET1", "chest": "…", "shoes": "…", "cape": "…" },
      "spells": { "q": "HOLYFLASH", "w": "PULSINGHEAL", "e": "HOLYEXPLOSION",
                   "d": "…", "r": "…", "f": "…" },
      "source": "EquipmentChanged" }
  ]
}
```

Comp Forge side (shipped): the "connect live party" button polls every
5s, "load party into comp" maps `weapon` → party slots, and live sync
keeps weapon, real Q/W picks and worn kit flowing into the loadouts.

## Optional loot module (researched 2026-08-13 — PROPOSAL, not built)

The guild-standard tool is **`matheussampaio/ao-loot-logger`** (Node.js,
GPL-3.0, 42★, actively maintained — pushed 2026-07, items auto-fetched per
patch via CI). Same local packet-reader architecture as our companion. Its
handler set documents the loot protocol: `OtherGrabbedLoot` (who looted
what from whose body), `NewLoot`/`NewLootChest`/`AttachItemContainer`
(containers appearing), `InventoryPutItem` (deposits), plus
`NewCharacter`/`CharactersStats` for name resolution. Output: local log
files consumed by `ao-loot-logger-viewer` (web). Ecosystem: a transparent
fork (`juniorafonso/LootLogger`, GPL), a stale C# variant (2022), viewers
and a log combiner.

Integration paths, in order of preference:

1. **Interoperate, don't vendor**: ingest ao-loot-logger's log FILES
   (pipeline parser → per-fight loot ledger joined to roster + comp +
   killboard outcome). Zero GPL exposure (consuming output ≠ derivative),
   zero capture-code maintenance, and guilds already run the tool.
2. **Native handlers in our companion** (later): add the loot event
   handlers to our MIT-stack reader — reimplemented from protocol facts,
   not copied GPL code (~100–150 lines). Makes the companion a one-tool
   fight-night hub: roster + gear + spells + loot.
3. **Not**: forking/embedding the GPL codebase into this repo (license
   contamination + a second Node stack to maintain).

## Risks / open questions

- Event code drift per patch (mitigated: SAT `EventCodes.cs` as reference;
  companion should fail loud when codes stop parsing, never silently).
- Raw-socket mode needs admin; Npcap mode needs Npcap installed — pick one
  as default UX (lean: Npcap optional, fall back to raw sockets + prompt).
- Unverified: whether the inspect response carries spells on the wire (SAT
  ignores them there; the companion takes a 14-slot array opportunistically
  since 2026-09-06 and `--debug` reports `sp=14`/`sp=` either way); whether
  the inspect shape itself still holds on the current patch (first live
  inspect with `--debug` confirms — `/status` `detected_codes.Inspect`);
  whether the gear-change event fires for ALL party members on zone-in or
  only on change (observed: gear arrives on visibility — NewCharacter
  carries equipment AND spells — and on change; the inspect response is
  the on-demand refresh for everyone else).
- Windows-only as scoped (capture stack).
